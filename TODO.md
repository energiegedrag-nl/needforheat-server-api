## Soon: robustness and correctness

- [ ] <a id="admindocs"></a>**Document admin, app, campaign and account creation.** Document the curl runbook for creating admins, apps, device types, campaigns and accounts in this repository.
- [ ] <a id="logs"></a>**Clean up the log and keep idle database connections alive.** The log of 2026-11-22 shows (1) lines `Error fetching source for ID 1: sourceID not found` (IDs 1–4) many times, without timestamp or log level: find which request causes them and log once with context; (2) every upload also logs the full device struct and a line `<nil>`: debug output that should go or move to debug level; (3) `[mysql] closing bad idle connection: connection reset by peer` / `broken pipe`: set `SetConnMaxLifetime` and `SetConnMaxIdleTime` below MariaDB's `wait_timeout`. A clean log matters for diagnosing upload gaps (→ [stall](https://github.com/energiegedrag-nl/needforheat-generic-firmware/blob/main/TODO.md#stall)). Raised by the maintainer on 2026-11-24.
- [ ] <a id="reuse"></a>**Return a device and hand it out again, keeping its history.** A device can belong to only one account forever; 'device already registered to another account' then blocks re-use. The old workaround (clearing or changing `device.account_id` in the database) moves the earlier measurements to the next participant and loses how long the device served whom. Design (archive instead of detach): (1) **server**: `POST /admin/devices/{name}/release` (admin port 8082) sets a new column `device.released_at` and renames the device to `<name>~<yyyymmdd-hhmm>`; it stays with its account, uploads and measurements, so the service period is `activated_at` to `released_at`, and the name is free for `POST /device` by the next account. Uploads and activation with a token of a released device get **410 Gone**, so nothing lands with the previous participant. The inventory gets a `return` event. App lists per account need no change: the next account sees only its own new device row. (2) **Cockpit**: a button *Retour ontvangen* per device in the inventory and the campaign status, with confirmation and the service period; the archived device stays visible with the previous participant. When the flash station meets a device that is still linked (assigned, shipped, returned or activated by the app), it asks whether the device goes to another participant (release) or back to the same one after a repair (keep the account). Server part and Cockpit: in progress (20-11-2026; return now keeps the account, ship from returned, release event, POST /admin/devices/{name}/release, 410 on upload). (3) **firmware** (needforheat-generic-firmware): on 410 the device erases its bearer and provisioning state and drops measurements still buffered (they belong to nobody), then shows the provisioning QR, so it is ready for the next participant even when it goes there directly, without the lab; by hand the existing Wi-Fi reset (top button 10 s) or a flash with full erase does the same. An earlier CO2 calibration stays valid. (4) **app**: show 410/'released' clearly instead of a generic error. Keep the proof-of-possession check for devices that are not released: only the researcher (Cockpit) releases a device. Done by hand on 19-11-2026 for device 1 (`FE2E-979798` -> `FE2E-979798~20261119`, account 4). Also affects: energiegedrag-cockpit, needforheat-generic-firmware, needforheat-gearup-app.
- [ ] <a id="tokens"></a>**Token lifetimes and abuse protection.** Decide and implement lifetimes for account activation, account, device activation and device tokens. Account numbers are sequential; rate-limit activation attempts so they cannot be guessed or flooded. Earlier proposal: account activation token 2 weeks (researchers can issue a fresh one), account session token 13 months, device session token 13 months (longest study about a year); the device's proof of possession never leaves the device.
- [ ] <a id="cockpitflow"></a>**Cockpit as a step-by-step plan, with a practice campaign.** Redesign the Cockpit GUI (energiegedrag-nl/energiegedrag-cockpit) around a recommended order of steps for a campaign manager (e.g. set up campaign, data sources, vault and key, participants, invitations, devices, monitoring, closing), so a new manager does not have to think long about what comes next. Steps stay directly reachable, except steps that depend on an unfinished earlier step (e.g. no invitations before the campaign and the vault exist). Add a practice campaign, as in AnonyMate's practice mode: made-up participants and data, clearly marked, nothing sent or stored on the real server, to click around safely before the first real campaign.
- [ ] <a id="cockpitvault"></a>**Cockpit vault: mail via energiegedrag.nl and helpdesk alias.** Follow-up of the local vault ([docs/kluis.md](https://github.com/energiegedrag-nl/energiegedrag-cockpit/blob/main/docs/kluis.md)): send invitations from the server through the energiegedrag.nl mail server for campaigns where the admin enabled it, and a helpdesk alias per campaign (helpdesk-<campaign>@energiegedrag.nl forwarding to the campaign manager). Own mail servers stay with the manager's own mail program (mailto/.eml): no mail credentials on the server.

## Later: features and ideas

- [ ] <a id="apivalidate"></a>**Reject apps with an empty name.**
- [ ] <a id="apidocs"></a>**API and provisioning documentation.** Turn the provisioning slides (PDF) into Markdown/MkDocs and check the OpenAPI description against API v3. OpenAPI docs already exist at `/docs` (served by the API); what is missing is up-to-date provisioning documentation. Key design rule: only the domain is fixed at build time, everything else reaches app and device at run time. Also affects: needforheat-generic-firmware.
- [ ] <a id="bt"></a>**Register phones for presence detection.** Let the app read the phone's static Bluetooth address and store it per account under a random ID; let presence detectors fetch the list instead of configuring it by hand. Also affects: needforheat-gearup-app, needforheat-presence-detector-firmware, needforheat-living-room-module-firmware.
- [ ] <a id="cloud"></a>**More cloud data sources.** Support Toon, Netatmo (Healthy Home Coach CO2) and Google Nest via OAuth2; let the app revoke a grant. Enelogic: treat month, day and interval data separately and test re-granting after an expired refresh token. Enelogic: a refresh token that is not used for about a month can no longer be refreshed; the user must grant access again. Also affects: needforheat-gearup-app.
- [ ] <a id="cockpit"></a>**NeedForHeat Cockpit (web portal).** Web portal for researchers: campaigns, accounts, invitations, data-flow monitoring, browser-based firmware flashing. Design: [docs/ontwerp.md](https://github.com/energiegedrag-nl/energiegedrag-cockpit/blob/main/docs/ontwerp.md) in energiegedrag-cockpit. Related: server-side clock-skew correction from device vs server upload time, KNMI 10-minute weather data, verifiable deletion requests, pseudonymous participant login, EU Data Act obligations.
- [ ] <a id="ha"></a>**Home Assistant as a data source.** A new kind of data source next to devices, cloud feeds and energy queries, for participants who run Home Assistant. Do not assume HA and the campaign server share a network. Decisions so far: an own HA integration (HACS) pushes data outbound to the campaign server, paired in the app with a code like a device and holding its own token; the campaign defines which properties it needs and the participant picks an HA entity per property, with suggestions from `device_class` and unit, converted to physiquant units; on pairing it also uploads history (long-term statistics, recorder data where available) in chunks. Data of interest: smart meter (DSMR), heat pump, EV charger (e.g. SmartEVSE, to separate charging from household use), indoor climate and thermostat, CO2 sensors (e.g. IKEA ALPSTUGA), ventilation systems. Needs: a data source type and pairing endpoint on the server, an onboarding flow in the app, manuals, and a new repository for the integration. Also affects: needforheat-gearup-app, needforheat-manuals.
- [ ] <a id="heatpump"></a>**Homes without gas: heat pumps and electric vehicles.** NeedForHeat targets gas-heated homes. For all-electric homes, campaigns need heat pump electricity (separate from EV charging and other use) and preferably heat delivered; the analysis needs a heat pump model (COP as a function of supply and outdoor temperature). Also affects: needforheat-gearup-app.
